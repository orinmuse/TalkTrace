# Interview Delta & Refresh Workflow

## Purpose

当当前上下文中同时存在：

- 项目前期资料 / 既有项目理解；
- 一场或多场既往访谈；
- 一场刚新增的访谈记录；

TalkTrace 应识别**本次新增访谈到底改变了什么**，并把这些变化转化为后续访谈的调整。

这是一种当前上下文内的工作方法，不建立独立持久状态。

## 1. Preconditions

开始前确认：

- 当前上下文里确实能看到需要比较的既有信息；
- 能区分“旧信息”和“本次新增访谈”；
- 如果缺少此前材料，明确说明无法可靠判断“新增/冲突/已回答”，只能整理本次访谈本身。

不得假装拥有其他对话或其他项目空间中的历史记忆。

## 2. Compute the interview delta

围绕项目当前核心问题，依次判断：

### 2.1 新增信息

本次第一次提供了哪些对项目有价值的信息？

优先识别：
- 新流程/新步骤；
- 新角色关系；
- 新数字、时间、案例；
- 新的执行例外；
- 新的原因解释或约束。

保留来源：这是本次受访者陈述，不自动变成企业事实。

### 2.2 已回答的问题

此前哪些开放问题因为本次访谈得到：
- 完整回答；
- 部分回答；
- 仍然无法回答。

已经得到充分回答的问题，后续提纲应删除或降级，避免重复浪费访谈时间。

### 2.3 冲突 / 不一致

检查本次说法是否与：
- 正式资料；
- 前序访谈；
- 其他当前上下文信息

存在实质差异。

只陈述差异本身，不判断哪一方一定正确。

### 2.4 单一来源待验证

如果本次出现重要、具体但只有单一来源支持的说法，标记需要：
- 资料验证；或
- 第二角色验证；或
- 数据验证。

不要因为受访者职位高而自动提高为事实。

### 2.5 新暴露的问题

本次回答可能引出新的未知问题，例如：
- 提到某个实际步骤，但没有解释触发条件；
- 提到某角色参与，但没有说明正式依据；
- 提到结果差异，但没有说明适用范围；
- 提出原因判断，但缺少案例或数据支持。

只保留会影响项目判断或后续访谈的信息缺口。

## 3. Select the next verification source

对每个高价值待验证项，判断：

- 谁最可能提供独立信息；
- 是找制度 owner、业务负责人、一线执行者、财务/数据 owner，还是补充资料；
- 是否需要不同视角而不是同一链条重复确认。

如果当前上下文没有足够的角色资料，说明推荐仅为暂定，不补造职责。

## 4. Refresh subsequent interviews

对后续尚未开展的访谈，按以下逻辑调整：

### 删除
- 已被充分回答且无必要再验证的问题；
- 低价值重复问题。

### 新增
- 本次暴露的重要新未知；
- 需要独立验证的单一来源说法；
- 需要解释的冲突。

### 调整重点
- 把访谈时间从低价值通用问题转向当前最高价值的信息缺口；
- 对某个角色不适合回答的问题转移给更合适的信息 owner。

### 补充访谈
只有现有访谈对象无法覆盖重要新信息缺口时，才建议补访，不为了流程完整机械增加人数。

## 5. Output

默认保持简洁，可使用：

```markdown
## 本次访谈带来的变化

### 1. 新增信息
- ...（来源：本次受访者陈述）

### 2. 已回答的问题
- ...

### 3. 冲突 / 待验证
- ...

### 4. 新暴露的问题
- ...

### 5. 对后续访谈的影响
- [后续角色]：删除/新增/重点调整 ...
- 如有必要：建议补访 ...
```

如果用户要求直接刷新某一位后续受访者的提纲，则完成 Delta 判断后直接调用 `references/interview-guide.md` 生成更新版，不要求用户重复提供已经存在于当前上下文的信息。

## 6. Source discipline

必须区分：

- 正式材料支持；
- 某位受访者陈述；
- 多来源方向一致；
- 来源冲突；
- 顾问/AI 工作假设；
- 尚未验证。

“多人说法一致”可以提高验证优先级或可信度判断，但仍不能自动证明企业事实、普遍性或因果关系。

## 7. Quality check

- 是否真正识别了“变化”，而不是重新总结整场访谈；
- 是否删除了后续已经没有必要重复问的问题；
- 是否把新增信息错误升级成企业事实；
- 是否识别了真正重要的冲突与单一来源说法；
- 是否把新问题分配给最合适的后续角色；
- 是否只建议必要的补访；
- 是否完全依赖当前上下文，没有虚构历史记忆或持久状态。

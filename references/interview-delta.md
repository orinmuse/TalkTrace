# Interview Delta & Refresh Workflow

## Purpose

TalkTrace 使用当前任务中可访问的项目资料和访谈语料，识别哪些问题已经回答、哪些信息冲突或仍需验证、又暴露了哪些新问题，并据此刷新后续访谈。

**默认 Mode C｜日终批次回传 / 次日行动刷新**：允许顾问每天结束后一次上传一至数个部门的自然语言纪要和资料，不依赖现场逐轮输入。

同时兼容两种历史输入模式：

- **Mode A｜单场新增访谈刷新**：既有项目/访谈上下文中刚加入一场新访谈，需要判断“这次新增到底改变了什么”；
- **Mode B｜多场历史语料整体刷新**：授权工作区或当前会话已经存在多场完成访谈，需要基于整个语料统一刷新剩余访谈，不要求其中必须有一场可被定义为“最新新增”。
- **Mode C｜每日批次刷新**：本批与之前资料能区分时记录真正增量，并修正已有认识；只有本日一个部门也能推进有界判断。

这是一种本次上下文内的工作方法，不建立独立持久状态。

## 1. Stateless reload preflight

在判断新增、已回答、冲突、待验证或下一场重点之前：

1. 如果任务依赖前序项目/访谈历史，先检查宿主当前是否能访问用户已授权工作区中的相关现成文件；
2. 读取与当前任务直接相关的项目资料、既往访谈纪要/转写、访谈汇总、已有访谈计划或剩余受访者信息；
3. 把读取到的普通文件视为本次当前项目材料，再进行 Refresh；
4. 不创建新的状态文件，不自动写回“记忆”，不把宿主文件访问能力解释成跨会话记忆。

如果相关历史文件不能访问或不存在，明确说明缺少可靠历史上下文。可以请求最少必要文件，或者只对当前可见材料给出边界清楚的暂定结果；不得假装拥有其他会话中的记忆。

## 2. Preconditions by mode

### Mode A｜单场新增访谈刷新

应能看到：

- 项目前期资料或既有项目理解；
- 一场或多场前序访谈（如已有）；
- 本次刚新增的访谈记录。

为了判断“本次新增了什么”，需要能区分既有信息与本次新增访谈。如果无法区分，只能转为 Mode B 的整体刷新，不能伪造逐场增量。

### Mode B｜多场历史语料整体刷新

应能看到：

- 项目目标/资料或足以界定当前调研问题的上下文；
- 多场已完成访谈语料或结构化纪要；
- 如需直接更新具体后续访谈，最好还能看到剩余受访者/角色信息。

**不要求**把多场历史语料切分成“旧状态 + 最新一场”。该模式直接从整个当前语料重建当前验证状态。

### Mode C｜日终批次处理规则

1. 先按实际文件日期、受访角色或用户说明识别**本批和前批**；无法判断新旧时，改为整体综合，不伪造“今日变化”。
2. 真实读取前序授权的项目资料和既往访谈；资料缺失则只分析本批，**不能可靠比较昨天**。旧版进展摘要只能定位来源，不是独立证据。
3. 识别当日新增真实案例、流程与责任、是否重复或仅有个例、结果证据、反例/冲突；每个重要判断保持来源范围。
4. 原判断被新证据限定或推翻时主动修正，不只是追加摘要；已解决/低价值问题从下一日清单删除。
5. 让下一日每位受访者承担独特信息任务，优先指向具体项目、真实工作样本、最可能掌握的角色或记录；未提供日程时不伪造“明天有人可访”。
6. 仅一个部门的一日资料也可以形成有用判断，但组织级重复性、普遍性、因果效果仍应保持未验证；新增资料没有实质信息价值时停止增加动作。

默认成果可压缩为“今日新增与修正 / 仍待核清 / 次日行动”。用户无需填表或维护专门台账。

## 3. Build the current interview state

无论 Mode A 还是 Mode B，都围绕项目当前核心问题判断以下状态。Mode A 额外标记哪些变化由本次新增访谈触发；Mode B 则对整个语料做合并判断。

### 3.0 Topic coverage｜更新主题覆盖，而不是只更新案例链

如果本轮调查是管理体系现状摸底，先根据当前项目范围和已有材料维护一份轻量主题地图。只记录会影响后续访谈的核心主题，不建立全量台账。

每个主题的覆盖状态可简记为：
- **尚未了解**：当前材料/访谈没有实质信息；
- **部分了解**：已有局部规则、单一角色视角或有限案例，整体结构/实际运行仍不清楚；
- **当前范围内基本摸清**：核心组成、适用范围和主要运行方式已有足够信息支持本轮现状描述；不代表其中每个主张都独立核实；
- **不适用/超出范围**：有当前项目范围依据，明确不属于本轮调查。

覆盖状态不是成熟度评分、可信度评分或完成百分比。**主题覆盖与主张证据验证必须分开**：主题已经讨论过，关键说法仍可能待核实；制度文件可以使正式设计较清楚，但实际运行仍可能部分未知。

每次日终批次检查：
1. 新信息是否补足某个主题，或改变其适用范围/模块结构；
2. 是否发现正式设计、实际运行和主体理解之间的差异；
3. 哪些核心主题仍未了解，是否确实属于项目范围；
4. 哪些主题虽已覆盖，但仍有重要主张需要独立核实；
5. 下一位受访者/资料 owner 最适合补足哪个主题或核验哪项主张。

只在主题覆盖变化会影响下一步时向用户呈现，不强制输出矩阵或覆盖率。

### 3.1 新增信息 / 新证据

识别第一次出现或相对既有状态新增的有价值信息，例如：

- 新增或修正的模块、制度、适用对象或范围；
- 新规则、职责分工、模块接口或数据口径；
- 新的实际运行方式、角色关系或执行差异；
- 新数字、时间、案例和可回查记录；
- 新的例外、体验反馈、约束或原因解释。

Mode B 如果无法证明某条信息是“最近新增”，不要强行标记时间顺序，只说明当前哪些来源支持该信息。

保留来源：访谈陈述不自动变成企业事实。

### 3.2 已回答的问题

对原有或当前核心开放问题判断：

- 已充分回答；
- 部分回答；
- 仍然无法回答。

已经得到充分回答、且无交叉验证价值的问题，后续提纲应删除或降级，避免重复浪费访谈时间。

### 3.3 冲突 / 不一致

检查不同来源之间是否存在实质差异，包括：

- 正式资料 vs 访谈；
- 不同受访者之间；
- 访谈汇总 vs 原始纪要；
- 其他当前可访问项目材料之间。

只陈述差异本身，不判断哪一方一定正确。Mode B 应保留冲突的来源范围，不因为“多数一致”自动消除少数来源。

### 3.4 单一来源待验证

重要、具体但只有单一来源支持的说法，应标记需要：

- 资料验证；或
- 第二角色验证；或
- 数据验证。

不要因为受访者职位高而自动提高为事实。多场语料中如果多名受访者方向一致，可以提高可信度或调整验证优先级，但仍不能自动证明普遍性或因果关系。

### 3.5 新暴露的问题

回答可能引出新的未知问题，例如：

- 新发现某个管理模块、规则或接口，但其适用对象/范围尚不清楚；
- 提到某个实际步骤，但没有解释触发条件；
- 提到某角色参与，但没有说明正式依据；
- 提到结果差异或主体体验，但没有说明适用范围；
- 提出原因判断，但缺少案例或数据支持。

只保留会影响项目判断或后续访谈的信息缺口。

### 3.6 Claim-level evidence record｜重要主张的三轴记录

只对会影响项目判断、后续访谈或行动优先级的重要主张维护轻量记录，不给每句话建立台账。每条重要主张分开记录三个维度：

**A. Evidence basis｜证据基础**

记录当前信息来自什么，以及来源对信息的接触程度：

- 正式制度、流程或授权文件；
- 系统记录、业务数据或可回查材料；
- 当事人亲历的具体案例；
- 非亲历转述；
- 个人判断、评价或原因解释。

必要时补充来源是否直接接触事件、职责/观察范围、距事件的时间、是否与其他来源共享上游信息，以及可能影响其观察范围的角色关联。角色关联只作为信息局限背景，不据此推断动机或诚信。

**B. Scope｜适用范围**

明确当前证据实际覆盖的对象和时间：

- 单一事件 / 单个项目；
- 某个岗位、角色或团队；
- 多个团队 / 部门；
- 组织整体；
- 明确的时期、项目类型或适用条件。

范围不能超出证据覆盖范围。单一案例只能支持案例级描述；要判断频率或组织普遍性，需要适当的跨案例、连续数据或有代表性的覆盖证据。

**C. Verification status｜验证状态**

验证状态与证据基础、适用范围分开记录。采用定性描述，不是线性评分：

- **待验证**：当前证据尚不足以支持所需判断；
- **在限定范围内得到支持**：证据与主张类型匹配，但尚未获得独立来源佐证；
- **在限定范围内获得独立佐证**：至少有实质独立、口径和范围相容的来源支持；
- **存在冲突**：来源之间存在实质差异，双方均保留；
- **仍未解决**：已检查可用来源，仍无法作出可靠判断；
- **满足当前用途**：证据足以支持本轮有限决策，必须同时注明适用范围，不代表普遍或永久成立。

三个维度互相独立，不要求按顺序依次升级。例如，一份正式制度可以是“证据基础=制度文件、范围=制度适用对象、验证状态=在制度设计范围内得到支持”，但实际执行仍可能待验证。

**最小记录示例**

> 主张：运营中心会调整项目月度进度。  
> 证据基础：一名运营人员亲历的单次案例；系统修改记录待查。  
> 范围：某项目、某月份。  
> 验证状态：案例范围内得到支持；调整频率和正式权限仍待验证。  
> 下一步：核对修改记录，并向直接经办人确认。

状态更新规则：

1. 新访谈只改变其实际提供的信息，不自动改变其他主张。
2. 单一案例可以支持案例级主张，但不能直接支持“通常如此”或“组织普遍如此”。
3. 文件只支持文件本身覆盖的主张；制度规定不等于实际执行，业务记录也不自动证明因果。
4. 多来源只有在信息来源实质独立、定义/时间/范围相容时，才构成独立佐证；共享上游信息不得重复计数。
5. 出现冲突时先检查定义、时间、对象和口径，不按职位高低或多数表决。
6. 没有找到证据、受访者不知道或当前材料未覆盖，不等于该事项不存在。
7. “满足当前用途”必须说明适用范围；后续用途或风险提高时，重新检查证据是否充分。

### 3.7 Evidence-fit and independence check｜证据适配与独立性检查

每个重要主张先判断其类型：正式规则、实际事件/做法、发生频率、角色权限、原因解释或结果影响。再分别检查证据基础、适用范围和验证状态，避免把三者合并成一个模糊的“可信度”。

- 制度文件可以证明制度写了什么，不能单独证明实际执行；
- 一名亲历者可以支持其描述的经历，不能单独证明全公司普遍如此；
- 多人说法一致，若都来自同一上游材料，不算多份独立佐证；
- 数据显示结果变化，不自动证明变化由某一管理措施造成；
- 来源独立、亲历或职位较高，都不能替代对证据与主张适配性的检查。

### 3.8 Risk-proportionate verification and stop｜按风险核验与停止

- 探索性线索可以先保留为待验证主张；
- 影响重要决策的主张优先安排适配的独立来源或记录核验；
- 高影响、争议或高风险主张再考虑多角色、材料/数据和反例组合。

当关键问题已在所需范围内得到支持、范围已被限定、下一步必须转向其他信息 owner，或继续访谈已没有决策增量时停止。证据仍不足则明确保留“仍未解决”，不为追求闭环而补造结论。

### 3.9 条件性实践穿透：“源—点—线—面—果—环”与证据控制分离

业务六层来自 `orinmuse/ai-maturity-assessment` 的真实业务实践调查方法，TalkTrace 只迁移调查逻辑，不套入其成熟度评分规则：

- **源 = 业务起因/目标**：为什么要开展这项管理做法、业务任务或改革，**不是资料出处**。
- **点 = 真实实践案例**：哪个项目、任务、人员何时做过什么，材料/样本如何回查。
- **线 = 实际工作过程与责任链**：沿同一案例前后穿透具体步骤、输入输出、参与角色、校核与成果采用。
- **面 = 重复性、组织范围及复制条件**：相似做法是否跨项目/人员/部门持续成立；单一案例不能证明组织稳定机制。
- **果 = 实际结果/价值**：质量、成本、效率、返工、客户或风险结果如何；主观评价与有证据支持的影响分开。
- **环 = 客户自身的反馈、调整、再运行和效果复核**：这不是 AI 日终再提问的循环；没有后续运行/验证，不能宣称持续改进。

六层是对**具体业务实践/能力形成与运行过程**的条件性调查逻辑，不是管理体系现状摸底的默认框架。对薪酬绩效、组织、岗位职级等体系现状调查，应先更新项目范围内的主题地图，再按需要对某些实际运行环节做专项穿透。对没有运行实例的制度设计项目，不能编造“点/果/环”；不要求每次、每个部门都满足六层。

**独立的证据操作**仍是本文件 §3.6–3.8 所述 Claim-level evidence record（重要主张）、Evidence-fit and independence check（适配与独立性）、Risk-proportionate verification and stop（按风险停止），分别记录 Evidence basis、Scope、Verification status、来源出处、关系与冲突。不得把证据出处、主张关系、覆盖状态重新称为业务六层的“源/点/线/面/环”。

**AI 的日批次更新循环**则是：实际读取当前项目证据 → 区分本日新增与前序 → 修正判断和问题 → 输出少量次日行动。它与客户组织内部的持续改进“环”是两种不同循环。

## 4. Select the next information source or verification source

下一步来源选择有两种互补任务：一是补足尚未了解的核心主题（主题覆盖）；二是核验会影响判断的重要主张（证据验证）。两者不要混为一谈。对每个高价值信息缺口或待验证项，判断：

- 当前需要补足的是哪个调查主题，还是核实正式规则、实际事件、频率、权限、原因或影响等具体主张；
- 谁最可能提供与该主题/主张匹配的信息；若任务是核验重要主张，再判断来源是否真正独立；
- 是找制度 owner、业务负责人、一线执行者、财务/数据 owner，还是补充资料；
- 对方是否亲自掌握信息，是否与现有来源共享上游信息；
- 是否需要不同视角而不是同一链条重复确认；
- 新来源会补足哪个主题覆盖缺口、提供哪种不同角色视角，或区分哪种竞争解释；
- 如果不同答案不会改变后续行动，则不增加这次追问；
- 获取材料或数据是否必要、已获授权且与判断风险相称。

如果当前上下文没有足够的角色资料，说明推荐仅为暂定，不补造职责。选择来源时不以职位高低替代实际信息掌握程度。

## 5. Refresh subsequent interviews

对后续尚未开展的访谈，同时依据**主题覆盖缺口**和**重要主张验证需求**调整；不要只围绕已出现的个案不断追问，也不要为了覆盖表格而机械增加访谈：

### 删除
- 已被充分回答且无必要再验证的问题；
- 低价值重复问题。

### 新增
- 当前语料暴露的重要新未知；
- 项目范围内尚未覆盖的核心主题、模块接口或关键角色视角；
- 需要独立验证的单一来源说法；
- 需要解释的冲突。

### 调整重点
- 把访谈时间从低价值通用问题转向当前最高价值的信息缺口；
- 对某个角色不适合回答的问题转移给更合适的信息 owner。

### 补充访谈
只有现有访谈对象无法覆盖重要新信息缺口时，才建议补访，不为了流程完整机械增加人数。

## 6. Output

默认保持简洁。用户若问“下一场怎么问”，应直接给刷新后的重点/提纲，而不是先暴露内部 Delta 表。

**日终批次默认交付**：

- **今日新增与修正的认识**：突出真正变化、之前哪些工作理解需要收窄/推翻；若旧资料不可读取，写“本批初步发现，不能可靠比较昨天”。
- **当前主题覆盖变化（按需）**：哪些体系模块/调查主题更清楚了，哪些仍未了解，正式设计、实际运行或主体理解是否出现新差异；只展示影响下一步的部分，不强制表格。
- **仍待核清的关键问题**：最有决策影响的主题缺口、制度/运行差异、重要主张、必要案例/数据/体验信息和反向样本，按现有覆盖范围表述。
- **次日访谈/资料核验行动**：对象/角色、要证实什么、一个自然问题或需要看的真实记录/案例。若无明确次日安排改写为“下一步”，不虚构日期或安排。
- 如果本批没有新增实质价值，说明无新增行动，不强制输出清单。

可以按请求附一页式《当前调研进展与下一日行动》交接快照，包含截至批次、范围、当前受限判断、未决点、下一步及原始文件定位；快照不是独立事实权威、不自动保存项目目录。

内部工作结果至少应能支撑：

```markdown
## 当前访谈状态

### 1. 新增/已确认的信息
- ...（保留来源与必要限定）

### 2. 已回答的问题
- ...

### 3. 冲突 / 单一来源待验证
- ...

### 4. 新暴露的问题
- ...

### 5. 对后续访谈的影响
- [后续角色]：删除/新增/重点调整 ...
- 如有必要：建议补访 ...
```

Mode A 可以突出“本次访谈带来的变化”；Mode B 应突出“基于多场现有语料形成的当前合并状态”，不得伪造某一场是最新增量。

如果用户要求直接刷新某一位后续受访者的提纲，则完成当前状态判断后直接调用 `references/interview-guide.md` 生成更新版，不要求用户重复提供已经从当前会话或授权工作区现成文件中读取到的信息。

## 7. Source discipline

必须区分：

- 正式材料支持；
- 某位受访者陈述；
- 多来源方向一致；
- 来源冲突；
- 顾问/AI 工作假设；
- 尚未验证。

“多人说法一致”可以提高验证优先级或可信度判断，但仍不能自动证明企业事实、普遍性或因果关系。

## 8. Quality check

- 若本轮是体系现状摸底，是否更新了项目范围内的主题覆盖，而不是把所有信息都压成案例/流程追问；
- 是否把主题覆盖状态与重要主张的证据基础、范围和验证状态分开；
- 是否区分正式设计、实际运行和相关主体的理解/体验；
- 是否根据主题缺口和证据核验需求选择不同的信息来源；
- 是否在依赖历史上下文时先执行了 Stateless reload preflight；
- 相关现成文件可访问时，是否先读取再 Plan / Guide / Refresh，而不是要求用户无意义重复上传；
- 相关历史文件不可访问或不存在时，是否明确降级且没有假装记得以前会话；
- Mode A 是否真正识别“变化”，而不是重新总结整场访谈；
- Mode B 是否能基于多场历史语料统一识别已回答问题、冲突、单一来源待验证、新暴露问题和后续重点，而不强制存在“最新一场”；
- 是否删除了后续已经没有必要重复问的问题；
- 是否把访谈陈述错误升级成企业事实；
- 是否把新问题分配给最合适的后续角色；
- 是否只建议必要的补访；
- 是否完全依赖本次可访问的当前材料，没有创建持久状态或虚构历史记忆。

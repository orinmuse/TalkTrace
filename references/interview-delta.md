# Interview Delta & Refresh Workflow

## Purpose

TalkTrace 使用当前任务中可访问的项目资料和访谈语料，识别哪些问题已经回答、哪些信息冲突或仍需验证、又暴露了哪些新问题，并据此刷新后续访谈。

支持两种输入模式：

- **Mode A｜单场新增访谈刷新**：既有项目/访谈上下文中刚加入一场新访谈，需要判断“这次新增到底改变了什么”；
- **Mode B｜多场历史语料整体刷新**：授权工作区或当前会话已经存在多场完成访谈，需要基于整个语料统一刷新剩余访谈，不要求其中必须有一场可被定义为“最新新增”。

这是一种本次上下文内的工作方法，不建立独立持久状态。

## 1. Stateless reload preflight

在判断新增、已回答、冲突、待验证或下一场重点之前：

1. 如果任务依赖前序项目/访谈历史，先检查宿主当前是否能访问用户已授权工作区中的相关现成文件；
2. 读取与当前任务直接相关的项目资料、既往访谈纪要/转写、访谈汇总、已有访谈计划或剩余受访者信息；
3. 把读取到的普通文件视为本次当前项目材料，再进行 Refresh；
4. 不创建新的状态文件，不自动写回“记忆”，不把宿主文件访问能力解释成跨会话记忆。

如果相关历史文件不能访问或不存在，明确说明缺少可靠历史上下文。可以请求最少必要文件，或者只对当前可见材料给出边界清楚的暂定结果；不得假装拥有其他会话中的记忆。

## 2. Preconditions by mode

### Mode A｜单场新增访谈刷新

应能看到：

- 项目前期资料或既有项目理解；
- 一场或多场前序访谈（如已有）；
- 本次刚新增的访谈记录。

为了判断“本次新增了什么”，需要能区分既有信息与本次新增访谈。如果无法区分，只能转为 Mode B 的整体刷新，不能伪造逐场增量。

### Mode B｜多场历史语料整体刷新

应能看到：

- 项目目标/资料或足以界定当前调研问题的上下文；
- 多场已完成访谈语料或结构化纪要；
- 如需直接更新具体后续访谈，最好还能看到剩余受访者/角色信息。

**不要求**把多场历史语料切分成“旧状态 + 最新一场”。该模式直接从整个当前语料重建当前验证状态。

## 3. Build the current interview state

无论 Mode A 还是 Mode B，都围绕项目当前核心问题判断以下状态。Mode A 额外标记哪些变化由本次新增访谈触发；Mode B 则对整个语料做合并判断。

### 3.1 新增信息 / 新证据

识别第一次出现或相对既有状态新增的有价值信息，例如：

- 新流程/新步骤；
- 新角色关系；
- 新数字、时间、案例；
- 新的执行例外；
- 新的原因解释或约束。

Mode B 如果无法证明某条信息是“最近新增”，不要强行标记时间顺序，只说明当前哪些来源支持该信息。

保留来源：访谈陈述不自动变成企业事实。

### 3.2 已回答的问题

对原有或当前核心开放问题判断：

- 已充分回答；
- 部分回答；
- 仍然无法回答。

已经得到充分回答、且无交叉验证价值的问题，后续提纲应删除或降级，避免重复浪费访谈时间。

### 3.3 冲突 / 不一致

检查不同来源之间是否存在实质差异，包括：

- 正式资料 vs 访谈；
- 不同受访者之间；
- 访谈汇总 vs 原始纪要；
- 其他当前可访问项目材料之间。

只陈述差异本身，不判断哪一方一定正确。Mode B 应保留冲突的来源范围，不因为“多数一致”自动消除少数来源。

### 3.4 单一来源待验证

重要、具体但只有单一来源支持的说法，应标记需要：

- 资料验证；或
- 第二角色验证；或
- 数据验证。

不要因为受访者职位高而自动提高为事实。多场语料中如果多名受访者方向一致，可以提高可信度或调整验证优先级，但仍不能自动证明普遍性或因果关系。

### 3.5 新暴露的问题

回答可能引出新的未知问题，例如：

- 提到某个实际步骤，但没有解释触发条件；
- 提到某角色参与，但没有说明正式依据；
- 提到结果差异，但没有说明适用范围；
- 提出原因判断，但缺少案例或数据支持。

只保留会影响项目判断或后续访谈的信息缺口。

## 4. Select the next verification source

对每个高价值待验证项，判断：

- 谁最可能提供独立信息；
- 是找制度 owner、业务负责人、一线执行者、财务/数据 owner，还是补充资料；
- 是否需要不同视角而不是同一链条重复确认。

如果当前上下文没有足够的角色资料，说明推荐仅为暂定，不补造职责。

## 5. Refresh subsequent interviews

对后续尚未开展的访谈，按以下逻辑调整：

### 删除
- 已被充分回答且无必要再验证的问题；
- 低价值重复问题。

### 新增
- 当前语料暴露的重要新未知；
- 需要独立验证的单一来源说法；
- 需要解释的冲突。

### 调整重点
- 把访谈时间从低价值通用问题转向当前最高价值的信息缺口；
- 对某个角色不适合回答的问题转移给更合适的信息 owner。

### 补充访谈
只有现有访谈对象无法覆盖重要新信息缺口时，才建议补访，不为了流程完整机械增加人数。

## 6. Output

默认保持简洁。用户若问“下一场怎么问”，应直接给刷新后的重点/提纲，而不是先暴露内部 Delta 表。

内部工作结果至少应能支撑：

```markdown
## 当前访谈状态

### 1. 新增/已确认的信息
- ...（保留来源与必要限定）

### 2. 已回答的问题
- ...

### 3. 冲突 / 单一来源待验证
- ...

### 4. 新暴露的问题
- ...

### 5. 对后续访谈的影响
- [后续角色]：删除/新增/重点调整 ...
- 如有必要：建议补访 ...
```

Mode A 可以突出“本次访谈带来的变化”；Mode B 应突出“基于多场现有语料形成的当前合并状态”，不得伪造某一场是最新增量。

如果用户要求直接刷新某一位后续受访者的提纲，则完成当前状态判断后直接调用 `references/interview-guide.md` 生成更新版，不要求用户重复提供已经从当前会话或授权工作区现成文件中读取到的信息。

## 7. Source discipline

必须区分：

- 正式材料支持；
- 某位受访者陈述；
- 多来源方向一致；
- 来源冲突；
- 顾问/AI 工作假设；
- 尚未验证。

“多人说法一致”可以提高验证优先级或可信度判断，但仍不能自动证明企业事实、普遍性或因果关系。

## 8. Quality check

- 是否在依赖历史上下文时先执行了 Stateless reload preflight；
- 相关现成文件可访问时，是否先读取再 Plan / Guide / Refresh，而不是要求用户无意义重复上传；
- 相关历史文件不可访问或不存在时，是否明确降级且没有假装记得以前会话；
- Mode A 是否真正识别“变化”，而不是重新总结整场访谈；
- Mode B 是否能基于多场历史语料统一识别已回答问题、冲突、单一来源待验证、新暴露问题和后续重点，而不强制存在“最新一场”；
- 是否删除了后续已经没有必要重复问的问题；
- 是否把访谈陈述错误升级成企业事实；
- 是否把新问题分配给最合适的后续角色；
- 是否只建议必要的补访；
- 是否完全依赖本次可访问的当前材料，没有创建持久状态或虚构历史记忆。

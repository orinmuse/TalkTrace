# Company Interview Guide Profile

## 1. Activation and authority

仅在用户要求公司格式、天强格式，或明确要求沿用其提供的公司提纲时启用。普通客户发送版继续使用通用模板。公司格式是按需表达层，不改变 TalkTrace 的事实边界，也不要求私有知识库、原始案例或其他 Skill 才能运行。

先识别项目目标、受访角色、发送对象、当前材料与时长。已知信息直接使用；信息不足时保留最少占位项，不要求用户维护表单。用户提供的当前项目模板优先于本 profile；任何格式都不得覆盖中性求证、来源保护与保密边界。

本 profile 是从多份历史专业提纲归纳的可复用候选规则，不宣称为公司已经正式颁布的统一规范。历史问题只能提供选题方法，不能证明当前客户的战略、业务表现、组织安排或改革计划。

## 2. Client-facing document structure

完整客户发送稿使用 `assets/interview-guide-company-client.md`：

1. 访谈邀请函：受访对象、真实委托与项目背景、主要议题、经确认的保密说明、署名、日期。
2. 访谈提纲：基本情况、项目核心主题、角色相关的支撑条件。
3. 补充意见与咨询期望：通常保留；专题访谈可按实际需要合并。
4. 致谢。

只要用户要问题清单、修改某一部分或内部版，就交付对应部分，不强行附完整邀请函。正式发送前删除使用说明和未解决占位项；关键信息不足时标记为待补的草稿，不称“可直接发送”。

委托未经确认时不得写“受贵单位委托”。公司名称、称谓、项目组和日期使用当前材料或用户明确指定信息，不从历史案例带入；不知道时用占位项。保密说明必须符合已确认安排；未确认时留“【待确认的保密说明】”，不能默认作出绝对保密承诺。录音、披露范围和敏感个人信息采集另按实际安排处理，不自动增加承诺。

## 3. Select topics by project type

先选项目主线，再按角色和信息缺口删改。主题和问题都是候选，不是每场必问清单；对混合项目围绕本次任务选取必要主题，不机械拼接所有题库。

| 项目类型 | 主要选题顺序 | 必须避免 |
|---|---|---|
| 战略规划 | 工作背景 → 发展回顾 → 业务与市场选择 → 关键资源能力 → 组织保障 → 实施重点 | 将历史战略口号、平台或业务优劣带入新客户；把所有未来方向写成已决定事项 |
| 组织与人力资源 | 发展要求 → 职责与协作 → 岗位及队伍 → 绩效与薪酬运行 → 约束与改进重点 | 预设岗位混乱、薪酬不公或绩效失效；用战略全题库稀释专项问题 |
| 治理与激励 | 工作背景与发展诉求 → 治理安排 → 对拟议事项的了解 → 态度与条件 → 规则建议及顾虑 | 将拟研究方案写成已批准；跳过知情条件追问个人出资；把不参与解释为不认同改革 |

治理与激励中，只有当前材料确认拟议安排时才直接问其具体内容；否则采用假设式探索。不论高层、职能还是骨干员工，都允许“不清楚”“暂不判断”“暂不考虑”。涉及个人参与或出资时，先明确用途、保密和自愿安排，允许跳过；没有当前需要不主动采集金额、持股比例等信息。

## 4. Differentiate the information job

同一项目保留共同主题，但问题层级和信息任务必须不同。

| 角色 | 优先获得的信息 | 取舍原则 |
|---|---|---|
| 公司领导 | 公司定位、业务组合、资源配置、重大取舍、改革边界、实施顺序 | 避免要求逐项还原部门操作细节；分管领导聚焦其实际分工 |
| 职能中层 | 部门履职、制度运行、职责接口、管理服务、队伍与数据支撑 | 仅问其熟悉范围的业务与市场判断，不要求代替领导决定公司战略 |
| 生产科研中层 | 业务及客户、竞争、项目或科研任务、资源协作、创新与实际支持需求 | 科研、生产、市场职责不同；按实际职责删除不适用的经营或研发问题 |
| 骨干员工 | 岗位体验、实际案例、对拟议方案的理解、个人顾虑和条件 | 不凭“骨干”称谓推定有资格、有参与意愿、出资能力或决策权 |

共同问题可用于独立验证，不因形式上重复就一律删除；已经充分回答且无交叉验证价值的问题才删除或降级。后续访谈新增的待验证点优先于静态题库。

## 5. Question wording and time selection

正式主问题用自然、开放的中文，例如“请您简要介绍”“您如何评价”“您认为”。一个主问题聚焦一个核心信息目的。复杂主题可以先主问，再以少量提示帮助理解；不要把十几个子题塞进一个长句。

客户发送版重点清晰、便于预先理解；顾问内部版可在对应主问题下保留当前依据、待验证点、可选案例追问及交叉验证，不在客户稿暴露内部假设、冲突标签或其他受访者意见。

先了解运行和评价，再对回答中确认存在的差距追问原因及建议。例如：“现有团队与工作要求是否匹配？如有差距，主要体现在哪里？”不要默认问“人员不足的原因是什么”。中性求证不等于全部改写成是非题。

对尚未调查的机制，把存在性判断放在主问题开头，而不是先预设再在句尾补“如果有”。例如先问“目前是否开展绩效评价？如有，如何运行”，不要先问“绩效评价如何运行”。骨干访谈先问“是否有认可或激励做法”，不能预设受访者已经获得支持、认可或激励。

拟议事项的条件性要保持到同一问题的结尾。仅讨论是否研究时，用“若开展相关研究，您希望关注什么”，不要在后半句回写成“本次研究”或“实施后的安排”。

问题清单省略邀请函时，不能连同必要的信息边界一起省略。涉及个人意见或拟议激励而信息使用、保密安排尚未明确时，简短说明“信息使用与保密安排尚待确认，交流开始前需先明确；您可跳过不便回答的问题”，不代项目组承诺已经确认或必将采取某项措施，也不索取敏感出资数据。将待确认事项与正式问题分清，不能把它藏在仅顾问可见的内部注释中。

按预计时长和优先级删并问题，给案例与现场追问留出空间；不设强制题数。需要时在内部版标记必问与备选；不要让用户为了使用模板先维护详细配时表。

## 6. Output check

- 项目类型和角色是否真实改变主题选择与问题层级；
- 是否仍以当前信息缺口而非历史题库组织提纲；
- 称谓、委托、署名、日期、保密说明是否有依据；
- 是否残留占位项、内部说明、其他客户名字或历史判断；
- 是否把拟议事项写成既定安排，或把评价性前提塞进问题；
- 问题是否能在约定时间内取舍并留出追问余量；
- 是否保留自愿与不确定回答空间；
- 是否在需要 Word 等真实文件时使用宿主能力，不能把文本称为已生成的文件。

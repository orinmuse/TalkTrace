# Interview Guide Workflow

## Purpose

基于当前上下文中的项目目标、已有证据、受访者角色和未决问题，形成真正有针对性的访谈提纲。

目标不是生成固定数量的问题，而是提高单位访谈时间的信息价值，并让后续访谈吸收前面已经获得的信息。

## 1. Establish the role's information job

在写问题前，先识别：

- 受访者的正式职务/职责（仅限材料支持部分）；
- 该角色与项目问题的关系；
- 这个角色最有可能提供的独特信息；
- 当前资料和既有访谈已经回答了什么；
- 哪些问题仍然未知；
- 是否存在需要该角色帮助解释或交叉验证的冲突。

如果职责资料缺失，可以基于明确职务形成暂定初稿，但不得补造具体职责或非正式权力。

## 2. Use the evidence-to-question chain

每个核心问题内部遵循：

`当前证据 → 仍未知什么 → 为什么这个角色可能回答 → 中性主问题 → 回答后可选追问`

没有清晰信息目的的问题应删除或合并。

优先获取：

- 实际发生了什么；
- 实际步骤如何形成；
- 在已经确认存在的步骤中，谁做什么；
- 数据/规则来自哪里；
- 最近真实案例；
- 正式规则与实际运行是否一致；
- 例外情形；
- 受访者对约束、原因和改进方向的判断。

不要把访谈变成抽象态度问卷，也不要重复询问当前材料已经明确、且没有必要核实执行差异的简单事实。

### 2.1 Answer-conditioned probing｜回答驱动的条件追问

追问不是把所有可能问题提前列出来，而是根据受访者刚才的回答选择下一项最有信息价值的探询。内部推理遵循：

`主问题 → 回答判型 → 识别尚缺的关键维度 → 选择一个下一问 → 更新待验证项`

#### 回答判型与下一步

| 回答形态 | 下一步优先动作 | 不应做什么 |
|---|---|---|
| 概括性判断（如“通常会分析”“一直如此”） | 请对方举最近一次具体实例，确认其亲历程度 | 直接把“通常”当作已证实的频率 |
| 具体案例 | 只补齐当前缺失的时间、步骤、参与者、决策点、依据或结果 | 把所有维度逐项重复追问 |
| 原因解释 / 评价 | 询问判断依据、对应案例、例外或其他可能解释 | 把受访者的原因判断写成已验证因果 |
| 转述 / 听说 | 识别直接信息来源，或寻找可核验记录 | 把转述当成独立佐证 |
| 否认 / 表示没有 | 区分“确实没有发生”“本人未接触”“不在职责范围” | 把不知情等同于组织中不存在 |
| 不知道 / 不确定 | 记录未知，转向最可能掌握信息的角色或资料 | 反复施压要求猜测 |
| 与已有信息冲突 | 先澄清定义、时间、范围、对象和信息来源 | 以职位高低或多数意见直接裁决 |
| 提供制度 / 数据 / 记录 | 判断该材料实际支持哪一种主张及其适用范围 | 因有文件就推断实际执行完全一致 |

#### 可选择的追问维度

根据主张和回答选择必要维度，不要求全部覆盖。选择下一问时，优先考虑：

1. 当前未解决的主张是否会改变项目判断；
2. 哪个缺失信息最能区分现有竞争解释；
3. 当前受访者是否亲自掌握该信息；
4. 哪个最简短、负担最低的问题能够取得该信息；
5. 本轮只问哪一个最有价值的问题。

除非受访者自然地一次回答了多个维度，不要把案例、参与者、依据、范围和结果堆成一个复合追问；先问最关键的一项，再根据回答补问。不要为了“问得全面”而连续展开低价值追问。

1. **具体案例**：最近一次实际发生了什么？
2. **过程还原**：实际经历哪些步骤，先后关系如何？
3. **参与者与决策**：谁实际参与、提出、执行或作出决定？正式权限与实际做法是否一致？
4. **范围与重复性**：只发生在这个案例，还是其他情形也发生？有哪些例外？
5. **依据与痕迹**：依据什么制度、数据、系统记录或业务材料？是否存在可回查记录？
6. **反例与替代解释**：有没有相反案例？是否可能由项目类型、时间、资源或其他因素造成？
7. **影响与结果**：具体改变了什么？有没有前后数据或其他结果证据？

#### Evidence-fit｜证据与主张匹配

先明确正在验证哪一种主张，再选择证据：

| 主张类型 | 更匹配的证据 | 典型边界 |
|---|---|---|
| 正式规则 / 制度设计 | 制度、流程文件、授权文件 | 不能单独证明实际执行 |
| 某次实际事件 / 做法 | 当事人亲历案例、业务记录、系统痕迹 | 单个案例不能证明普遍性 |
| 发生频率 / 普遍程度 | 多个独立案例、连续数据或有代表性的记录 | 多人重复同一上游说法不等于独立样本 |
| 角色权限 / 决策权 | 正式授权依据与实际决策记录/亲历信息 | 职务名称不等于实际拍板权 |
| 原因 / 因果关系 | 时间顺序、对比案例、机制证据及竞争性解释 | 个人解释首先是待检验假设 |
| 结果 / 影响 | 前后数据、结果记录、受影响对象反馈 | 结果变化不自动归因于单一因素 |

#### Source independence｜来源独立性

交叉验证前检查不同来源是否真正独立：

- 是否由不同主体亲自观察或掌握；
- 是否都来自同一份会议纪要、同一位上级或同一条转述链；
- 对关键概念、时间段、对象和统计口径的理解是否一致；
- 是否存在相反案例或未被覆盖的群体。

共同上游信息不能重复计数。还应记录来源是否亲历、是否实际接触相关业务、距离事件发生的时间，以及其职责范围或可能的利益关联；这些只是判断信息可见范围和局限的背景，不得据此推断受访者不诚实。来源独立也不意味着内容必然正确；仍需检查证据与主张的适配性。

对重要主张，始终把三个维度分开：

- **Evidence basis｜证据基础**：文件、数据、亲历案例、转述或个人解释；并记录来源接触程度与来源关系。
- **Scope｜适用范围**：单一案例、某个角色/团队、多个部门或组织整体，以及对应时间段。
- **Verification status｜验证状态**：待验证、在限定范围内得到支持、在限定范围内获得独立佐证、存在冲突、仍未解决或满足当前用途。

不能把“文件支持”“单一案例”“已佐证”混成一条证据等级序列。前两者分别是证据基础和范围，后者才是验证状态。

#### Verification depth｜按风险确定核验深度

- **探索性线索**：允许先保留单一来源，但明确仅用于形成假设，不外推普遍性。
- **影响决策的关键主张**：优先增加一个真正独立且适配的来源或记录核验。
- **高影响、争议或高风险主张**：必要时组合独立角色、正式材料/数据、反例检查和范围限定。

不设固定访谈人数或统一证据数量。核验深度取决于判断的重要性、错误后果、现有证据质量及获取成本。

#### Stop condition｜停止追问

出现以下任一情况时，不再机械追问：

- 已获得足以支持当前所需范围的证据；
- 关键范围已被明确限定，且下一步应转由其他来源验证；
- 受访者不掌握信息，继续追问不会增加有效信息；
- 当前可访问来源已无法进一步区分竞争解释。

此时记录“已回答 / 范围受限 / 转交验证 / 仍未解决”，不得把停止追问解释为事实已经被证明。

### 2.2 Stage-aware use｜按访谈阶段启用源点线面环

源—点—线—面—环是内部推理方法，不是现场访谈必须逐项执行的流程。不同阶段启用重点不同。

#### A. 访谈准备｜用有限画像确定信息需求

- **源 + 点**：梳理当前项目资料、已有访谈和重要主张，区分材料明确、受访者陈述、推断与未知。
- **面**：当议题跨多个角色、流程或案例时，建立简要覆盖视图，判断哪些关键问题已有信息、部分有信息或尚未覆盖；简单单人访谈不要求矩阵。
- **线**：只梳理会影响提纲的既有矛盾、流程依赖、权责关系或竞争解释。
- **环**：据此选择最适合的信息掌握者、访谈顺序和本场主问题。

准备阶段的覆盖视图是暂定工作假设，不是完整组织画像；不得为了填满维度而机械增加访谈对象。

#### B. 现场访谈｜以源、点、环为主

当用户逐轮提供受访者回答并需要现场追问建议时：

- **源**：判断回答来自亲历、直接记录、转述、概括说法还是个人观点；不重复追问已明确的来源信息。
- **点**：抓住会改变判断或下一问的关键内容，不要求实时拆解每句话。
- **环**：根据刚才的回答，选择一个最有价值、最自然的下一问；如果受访者不掌握信息，则停止追问并转向适当来源。
- **线**：只在出现重要矛盾、流程顺序、角色权限、来源依赖或因果解释时，才在内部识别关系。
- **面**：不在现场完整构建或展示议题画像/覆盖矩阵；只利用已有的关键缺口指导提问。

现场问题应保持自然、简短、一次聚焦一个重点。不得为了完成五层结构而打断访谈、堆叠追问或展示“源/点/线/面/环”等内部标签。TalkTrace 只根据用户提供的回答工作，不假设自己能够自动听取或记录现场对话。

#### C. 访谈后整理｜源、点为基础，线、面按需展开

- 保留重要陈述、案例、记录及可用定位，区分“受访者这样说”“记录显示”和“顾问据此推断”。
- 对重要主张提取少量可回查信息点，明确其支持范围和不能支持的内容。
- 仅对影响判断或下一步行动的重要信息点建立关系；明确区分顺序、支持、矛盾、条件/例外、权责、来源依赖和因果假设。
- 当多来源或跨角色综合有价值时，更新有限议题画像，标出已覆盖、部分覆盖和未覆盖，以及共同点、差异、冲突与未知。
- 新信息可能推翻旧理解时，修正原有信息点、关系和画像，不只在旧摘要后追加新内容。

#### D. 跨场次刷新｜用当前证据决定下一场

基于本次可访问的全部授权材料，检查来源是否独立、关键关系是否成立、重要议题覆盖到什么范围，再选择下一位最合适的信息掌握者或下一份记录。后续提纲只呈现受访者需要回答的问题，不展示完整内部画像。

### 选择下一问的原则

1. 先判断缺口是否会改变当前项目判断或下一步访谈安排；
2. 判断当前受访者/资料是否真正掌握该信息；
3. 判断新来源是否能提供独立且与主张匹配的信息；
4. 选择成本最低、表达最自然的一个问题或资料请求；
5. 一次只问一个最有价值的问题；如果不同答案不会改变行动，则不追问。

简单、低风险、单一来源任务可以只做源和点的基本识别；出现关键冲突、跨角色机制或重要普遍性主张时，再扩展到线和面。这里的“面”是有限议题画像，不是正式管理诊断。

## 3. Premise-safety rule

### 3.1 Core rule

问题中任何会让受访者被迫接受为真的前提，都必须先有当前证据支持。

这不仅包括明显的主体、动作、流程环节和因果关系，也包括较弱的语义前提，例如：

- 某个检查、沟通、跟踪、审批、调整等环节**确实存在**；
- 某个动作发生后**一定还有后续处理**；
- 单一案例中的做法代表组织的**通常/一般/常规机制**；
- 某个角色**必然参与或拥有某项权力**；
- 某种先后顺序或稳定流程**已经成立**；
- 某个现象已经存在，因此可以直接追问“为什么”。

只有在以下情况下，具体前提可以直接进入问题：

1. 当前项目材料明确支持；或
2. 用户明确提供；或
3. 受访者在本次/此前回答中已经明确确认。

否则必须先确认“是否存在 / 是否发生 / 是否普遍”，再继续追问主体、频率、依据、例外、原因和影响。

### 3.2 Semantic premise gates

生成每个核心问题前，依次过以下语义 Gate。任何一项证据不足，都不能把它写成既定事实。

#### Existence gate｜存在性

先问：这个动作、环节、机制或关系是否已经被证据确认存在？

不安全：

> “结果形成后如何进行一致性检查？”

安全：

> “结果形成后是否还会经过其他检查、确认或处理环节？如果有，请介绍具体怎么做。”

#### Continuation gate｜后续处理

已知 A 发生，不代表 A 之后一定存在反馈、沟通、跟踪或二次处理。

不安全：

> “提交以后实际发生了哪些反馈或沟通？”

安全：

> “提交以后是否还有后续处理？如果有，通常包括哪些环节？”

#### Scope / recurrence gate｜范围与重复性

一个案例只证明“这个案例发生过”，不能直接证明“通常如此”。

如果当前只有单一案例，应先限定在该案例：

> “在刚才这个项目中，资源安排形成后是否还有后续跟踪？如果有，具体怎么做？”

再另问外推范围：

> “这种做法只发生在这个项目，还是其他项目也会采用？哪些情况下不同？”

没有重复来源、正式规则或受访者明确确认前，不得把“通常、一般、常规、一直、都会”作为默认前提。

#### Actor / authority gate｜主体与权力

已知某流程存在，不代表某个特定角色一定参与，更不代表其拥有正式或实际决定权。

先确认参与角色，再追问各自作用和边界。

#### Sequence / mechanism gate｜顺序与机制

不得因为常识或行业惯例，自动补出审核、复核、会签、沟通、跟踪等中间步骤。

先还原实际步骤，再对已确认步骤追问机制。

#### Causality gate｜因果

在“现象是否存在、范围多大”尚未确认前，不直接问“为什么会这样”。

先确认现象，再询问受访者的原因判断，并将原因保持为观点而非已验证因果。

### 3.3 Two-stage questioning

对于实际流程不清楚的主题，优先采用两阶段提问：

**阶段一：先还原真实发生的步骤。**

> “请以最近一次实际项目为例，介绍从方案形成到最终确定实际经历了哪些步骤。”

**阶段二：只对已经被确认存在的步骤继续追问。**

> “刚才提到其中存在一次调整。这个调整由哪些角色参与？主要依据是什么？”

如果需要判断该做法是否具有普遍性，再增加第三步：

> “刚才这个案例中的做法，在其他项目中也通常如此吗？哪些情况下会不同？”

### 3.4 Case-to-mechanism rule

单一访谈案例、单一受访者说法或一次具体事件，默认只支持**案例级问题**。

从案例上升为稳定机制前，至少需要：

- 正式材料支持；或
- 受访者明确说明这是重复/通常做法；或
- 其他独立来源提供一致支持。

否则后续提纲只能：

1. 验证该案例是否真实；
2. 验证相似情形是否重复出现；
3. 再判断是否存在稳定机制。

不得直接从“这个项目发生过”跳到“组织通常如何做”。

### 3.5 Unsafe wording examples

不推荐：

> “院级负责人通常在什么情况下会调整项目经理提交的建议？”

如果资料没有证明存在这一行为，这句话已经把“院级负责人会调整”写成前提。

也不推荐：

> “请介绍每一步由谁提出、调整、审核和确认。”

当资料没有证明“调整、审核、确认”都是实际步骤时，这种枚举同样会制造隐含前提。

也不推荐：

> “项目经理提供信息后，部门层面实际发生了哪些后续动作和沟通？”

即使没有指定具体动作，也预设了“部门层面一定存在后续动作/沟通”。

更安全：

> “项目经理提供信息后，部门层面是否还有后续处理？如果有，请介绍实际经历了哪些步骤、哪些角色参与。”

## 4. Role differentiation

不同角色必须承担不同的信息任务，而不是只换姓名和职位。

### 高层决策者

优先：
- 项目/改革目标；
- 管理原则与重大矛盾；
- 关键取舍；
- 权责边界；
- 改革节奏、不可突破边界和成功标准。

避免沉入大量字段、算法和操作步骤。

### 职能 owner

优先：
- 制度与规则；
- 实际流程；
- 数据来源、计算、审核；
- 正式规则与执行差异；
- 例外和争议处理；
- 与其他部门/角色的接口。

### 业务/生产负责人

优先：
- 项目实际运行；
- 工作量、资源与协同；
- 经营/绩效机制如何影响一线行为；
- 最近真实项目案例；
- 正式机制在业务端如何落地；
- 例外、堵点和执行体验。

### 一线/补充验证对象

优先：
- 具体操作；
- 实际体验；
- 例外情况；
- 对上游说法进行独立验证。

## 5. Use current context to avoid repetition

如果当前上下文已有前序访谈：

- 已经得到充分回答的问题应删除或降级；
- 只有单一来源的重要说法，应转化为中性验证问题；
- 已出现冲突时，问题应帮助解释差异，而不是直接选一方为真；
- 新出现的重要未知问题，应进入最合适的后续角色提纲；
- 单一案例只能支持案例级验证，不能自动生成“通常如何”的机制级问题。

不要机械复用项目开始时一次性生成的旧提纲。

## 6. Fit the guide to time

问题数量由预计时长和信息价值决定，不设置固定题数。

- 短访谈：少量高价值主问题；
- 中等时长：覆盖核心信息任务并预留追问；
- 长访谈：可以增加机制、案例和验证，但仍不追求面面俱到。

现场追问通常比“把预写问题全部问完”更重要。

## 7. Client-facing version

用户要求公司格式、天强格式，或明确沿用其提供的公司提纲时，同时读取 `references/company-interview-guide.md`，按项目类型与角色选题，并按需使用 `assets/interview-guide-company-client.md`。该表达层不替代本文件的前提安全与时间取舍规则；普通客户发送版不自动加公司品牌、委托或保密承诺。

适合提前发送给客户：

- 正式、简洁；
- 按少量主题分组；
- 不暴露内部假设、证据状态、冲突标签和顾问判断；
- 问题本身自然可理解；
- 不堆砌方法说明。

可使用 `assets/interview-guide-client.md` 作为轻量模板。

## 8. Consultant internal version

只增加真正帮助现场访谈的信息，建议包括：

- **当前已知信息**；
- **当前未决/冲突**；
- **为什么问这个角色 / 提问目的**；
- **正式主问题**；
- **可选追问**；
- **后续交叉验证**。

可使用 `assets/interview-guide-internal.md`。

没有实际价值的字段可以省略，不得为了填满模板制造内容，也不要把内部版做成复杂证据系统。

## 9. Premise preflight before output

完成前逐个检查核心问题。对问题中的每个事实前提都回答：

1. **存在性**：这个动作/环节/机制真的已被确认存在吗？
2. **后续性**：是否只是因为前一步发生，就擅自假设后面还有反馈、沟通、检查、跟踪？
3. **范围性**：证据只支持一个案例，还是足以支持“通常/一般/常规”？
4. **主体性**：是否擅自指定了参与者、owner 或决策者？
5. **顺序/机制**：是否补出了材料未确认的流程步骤？
6. **因果性**：是否在现象尚未确认前直接追问“为什么”？
7. **来源性**：是否把某位受访者的说法当成企业事实继续提问？

任何一项不通过，优先改成：

`是否存在/是否发生 → 如果有，具体是什么 → 谁参与 → 频率/范围 → 依据/例外 → 原因/影响`

而不是仅做措辞柔化。

## 10. Output quality check

- 这份提纲是否明显是为“这个人”写的；
- 是否使用了当前项目资料和既有访谈，而不是通用模板；
- 是否覆盖最重要的未决问题；
- 是否减少了已被前序访谈回答的问题；
- 是否存在任何显性或弱语义前提偷渡；
- 单一案例是否被错误泛化成稳定机制；
- 是否安排了必要的交叉验证；
- 在预计时长内是否可问完并留出追问空间；
- 客户发送版是否暴露了内部判断。

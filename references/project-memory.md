# Local Markdown Project Memory

## Purpose

把项目中可以跨任务、跨会话复用的背景、语境、信息状态和执行状态，保存为项目本地文件夹中的 Markdown。项目记忆服务于后续访谈工作，不替代原始材料，也不扩展为数据库、RAG、证据图谱或正式管理诊断。

## 1. Storage contract

默认在用户当前明确打开、提供或授权的项目根目录内使用：

```text
<project-root>/
├── <original project materials, unchanged>
└── talktrace/
    ├── project-memory.md
    ├── source-register.md
    ├── interviews/
    ├── working/
    └── history/
```

规则：

- `talktrace/project-memory.md` 是每次恢复项目时首先读取的入口；
- `talktrace/source-register.md` 是原始材料和访谈来源的登记表；
- `interviews/` 保存用户要求落盘的访谈纪要或访谈 Delta；
- `working/` 只保存确有复用价值的 Markdown 语义工作副本，不做全量强制转换；
- `history/` 只记录会改变项目理解、信息状态、访谈安排或下一步行动的重要更新；
- 不扫描、读取或写入用户未授权的其他项目目录；
- 不修改、移动、覆盖或删除原始项目文件。

## 2. First-use initialization

进入项目后先寻找 `talktrace/project-memory.md`。

### If it exists

1. 读取项目记忆 frontmatter 和正文；
2. 读取 `source-register.md`；
3. 检查结构是否可识别、项目身份是否一致；
4. 再按本轮任务读取必要的原始材料、访谈文件和工作副本。

### If it does not exist

在运行环境支持本地文件写入时：

1. 创建 `talktrace/` 及必要子目录；
2. 以 `assets/project-memory-template.md` 初始化 `project-memory.md`；
3. 以 `assets/source-register-template.md` 初始化 `source-register.md`；
4. 根据当前可访问材料登记来源并形成最小项目理解；
5. 不要求用户手工创建文件、填写 Schema 或维护编号。

如果运行环境不能创建或写入文件，应明确说明“本轮可以工作，但尚未形成可跨会话恢复的项目记忆”。不得把聊天上下文冒充已经持久化的项目记忆。

## 3. Project identity

`project-memory.md` 使用简短 YAML frontmatter：

```yaml
---
talktrace_memory_version: 1
project_id: stable-project-id
project_name: 项目名称
last_updated: YYYY-MM-DDTHH:MM:SS+08:00
---
```

- `project_id` 在首次初始化时生成，后续保持不变；
- `project_name` 来自用户说明或材料中的明确项目名称，未知时使用中性暂名并标记待确认；
- `last_updated` 只在文件成功写回后更新；
- 不生成与真实项目无关的身份、客户名称或时间。

## 4. Source registration

对进入项目工作链的原始材料和访谈来源分配稳定编号：

- 正式材料：`S001`、`S002`……
- 访谈来源：`I001`、`I002`……

登记内容至少包括：

- 来源编号；
- 文件名或来源名称；
- 相对路径；
- 文件类型；
- 日期/版本/最后修改时间（运行环境能够读取时）；
- 当前处理状态；
- 读取限制或重要说明。

文件内容哈希只有在宿主可稳定获得且确有必要时才记录，不把哈希设为日常使用前提。若发现同一路径的文件发生变化，应保留此前版本说明并把新状态标记为“已变化，待复核”或完成复核后的状态，不能静默把旧结论当作仍然有效。

## 5. Information model

项目记忆只保留会影响后续访谈和项目推进的信息，并在内部区分：

- **材料明确**：由原始材料直接支持；
- **访谈陈述**：某位受访者的来源信息；
- **初步工作理解**：可修正的顾问/AI 工作理解；
- **多来源方向一致**：多个相关来源相互支持，但不自动等于正式企业事实；
- **冲突/不一致**：不同来源存在实质差异；
- **待验证/开放问题**：证据不足，需要后续材料、数据或访谈确认。

每项重要信息应尽可能带来源编号或“用户本轮明确确认”等可追溯说明。不得为追求表格完整而制造来源编号、页码、时间戳、人物、事实或结论。

## 6. Project status

`project-memory.md` 至少保留以下当前状态，空项可省略：

- 当前项目阶段；
- 已完成的访谈与成果；
- 已安排/待开展访谈；
- 当前最高价值信息缺口；
- 关键决定及其来源；
- 阻塞项；
- 下一步行动、负责人和时间要求（如果已知）；
- 最近一次更新摘要。

项目状态是可执行状态，不是泛化项目总结。已经失效的状态不得继续放在“当前状态”中，应移入更新历史或标明已关闭。

## 7. Incremental update protocol

完成材料读取、访谈纪要、Interview Delta、访谈计划或明确项目决定后，判断是否有内容需要写回。

### Add

- 新材料或新访谈来源；
- 新出现且会影响后续工作的事实、陈述、案例、冲突或开放问题；
- 新的项目决定、阻塞或下一步行动。

### Change

- 开放问题被部分或完整回答；
- 工作理解被新来源修正；
- 访谈对象、重点或安排发生变化；
- 项目阶段或行动状态发生变化。

### Preserve

- 不受新信息影响的既有内容；
- 与新说法冲突的旧来源信息；
- 仍然有效的来源定位和限定词；
- 用户自行增加且 TalkTrace 不能确认用途的章节或字段。

### Never

- 用一份新摘要整体覆盖项目记忆；
- 把受访者陈述升级成“材料明确”；
- 为消除矛盾而删除冲突来源；
- 因文件无法读取而把此前信息标为错误；
- 在没有成功写入后声称项目记忆已经保存。

更新成功后：

1. 更新 `last_updated`；
2. 在“最近更新”中写明本次变化；
3. 对重要更新在 `history/YYYY-MM-DD-HHMM-memory-update.md` 写入简短 Delta；
4. 向用户只说明实际保存成功的文件和关键变化，不展示内部维护细节。

## 8. Read strategy

每次任务默认读取：

1. `project-memory.md`；
2. `source-register.md`；
3. 与本轮任务直接相关的访谈、原文件或工作副本。

不要为了一个局部任务重新读取全部项目材料。只有在来源变化、记忆冲突、关键定位缺失或用户要求全面复核时，才回到相关原始文件验证。

## 9. Failure and recovery

- 文件夹不可访问：说明无法加载或保存项目记忆，并请求用户重新提供/打开正确目录；
- 文件夹只读：可以读取和完成当前任务，但明确说明更新未持久化；
- 记忆文件缺失：从可访问原始材料重新初始化，不假装恢复了旧状态；
- 记忆文件结构损坏：停止覆盖原文件，优先读取 `history/` 和来源登记进行恢复；
- 项目身份不一致：停止写入，先确认是否打开了错误项目目录；
- 原始来源丢失：保留记忆中的历史记录，但标记“原文件当前不可访问，无法复核”；
- 并发或外部编辑导致内容变化：重新读取最新文件后合并，不用旧版本强制覆盖。

## 10. Quality check

- 新会话是否可以不依赖旧聊天恢复项目背景和当前状态；
- 原始文件是否保持不变且能够从来源编号回查；
- 新信息是否以增量方式更新，既有有效信息是否保留；
- 访谈陈述、工作理解与材料明确是否仍然分开；
- 冲突是否被保留而非静默解决；
- 当前状态、阻塞和下一步是否真实反映最新项目进展；
- 是否只声称完成了实际成功的文件写入；
- 是否避免把项目记忆扩展成正式诊断或重型知识系统。

# Public Cold-start Regression

## Purpose

验证第一次接触 TalkTrace 的用户使用普通自然语言时，Skill 能否在不要求用户学习内部模块、Workflow、Schema 或 `Delta` 术语的情况下，自然进入正确任务并先给出有用初稿。

这些 case 是**公开工程 regression evidence**，实现过程可以读取，不得单独用于宣称 Capability Accepted。

## Global assertions

所有 case 都必须满足：

- **先有用，再澄清**：能形成合理初稿时先做，不把用户挡在问卷前；
- **最少必要追问**：只追问会实质改变当前成果的信息；
- **不暴露内部机制**：普通用户不需要选择 Plan / Guide / Notes / Delta 模块，也不需要理解 epistemic state；
- **不编造**：不补造人员身份、具体职责、汇报关系、真实权力、流程步骤、可用时间、制度或数据；
- **有边界但不拒绝式降级**：输入不足时说明针对性限制，同时仍提供能继续工作的产出；
- **不把单一访谈升级成正式企业事实或正式诊断**。

## C1｜Broad ask with project materials

### Input

用户提供以下合成项目资料：

- 项目：某工程设计集团总部职能协同优化；
- 项目处于调研阶段；
- 总部设人力资源部、运营管理部、财务部；
- 下设三个生产院；
- 现有材料提出“减少重复数据报送、理顺总部与生产院接口”，但未说明具体重复数据、责任部门和实际运行流程；
- 已知拟访谈主要领导、总部核心职能和生产院负责人，但尚未形成具体顺序。

### User prompt

`这是客户资料，帮我准备一下访谈。`

### Expected behavior

- 不要求用户先选择“访谈计划 / 提纲 / Delta”；
- 识别这是访谈准备的 broad ask；
- 优先给出轻量的访谈准备初稿，例如：关键未决问题、建议访谈角色/对象、主要信息任务、建议时长或优先级；
- 不在没有时间窗口的情况下伪造正式日期/时间；
- 可简短指出正式排程还需要哪些约束，但不把这些问题变成开始工作的前置门槛；
- 不把“重复数据报送”直接写成已经确认的普遍事实，应把具体范围、触发场景、责任边界作为待验证内容。

### Regression fail examples

- 只回复“请先告诉我你要访谈计划还是访谈提纲”；
- 连续追问多个配置问题而不给初稿；
- 编造访谈人员姓名或可用时间；
- 直接假设运营部就是重复报送问题 owner。

## C2｜Named functional leader, no project context

### Input

无项目背景、无组织职责资料、无既往访谈。

### User prompt

`我要访谈人力资源部长，帮我准备一下。`

### Expected behavior

- 自然路由到访谈提纲/访谈准备，而不是要求用户学习模块名；
- 明确由于缺少项目目标和客户背景，无法做到真正高度针对性；
- 仍然给出可用的暂定访谈框架，围绕人力资源负责人通常可回答的制度、实施、跨部门接口、真实案例等信息类型；
- 不补造该公司的绩效制度、组织问题、HR 具体权限或当前改革背景；
- 如需追问，优先只问一个最能提高针对性的事项，例如“这次项目最想解决什么问题/方便补充项目背景吗”。

### Regression fail examples

- 凭空假设该公司存在绩效申诉、人才流失、招聘不足等问题；
- 因信息不足只拒绝生成；
- 一次询问五六项背景字段后才愿意开始。

## C3｜Plan request without scheduling constraints

### Input

用户提供合成组织名单与项目目标，但没有日期、访谈窗口、分组或人员可用时间。

### User prompt

`根据这些资料帮我制定访谈计划。`

### Expected behavior

- 先输出 **Quick Plan**：对象/角色优先级、建议时长、主要访谈目的、重点验证/信息缺口；
- 不伪造具体日期、时点、组别或 availability；
- 不为了形式完整立即要求用户补齐所有排程参数；
- 只有用户明确要求正式日程时，才询问会实质改变排程的时间窗口、组数、固定安排等。

### Regression fail examples

- 自动生成“9:00–10:00 董事长”等未经确认的正式日程；
- 只有职位名单，没有访谈目的/信息缺口；
- 完全停止输出并要求先回答排程问题。

## C4｜Natural refresh request

### Input

当前上下文已经存在：

- 前期资料；
- 一场刚完成的人力资源负责人访谈；
- 下一位拟访谈对象为运营管理部负责人。

人力资源负责人在访谈中明确：

- HR 组织绩效流程，但经营数据主要来自运营与财务；
- HR 无法确认运营是否会在汇总后统一调整各生产院产值；
- HR 听到过生产院对重复报数和口径解释的反馈，但认为应直接向生产院和运营确认。

### User prompt

`结合刚才这场访谈，帮我更新下一场运营负责人的访谈重点。`

### Expected behavior

- 用户无需说 `Delta`；
- 内部识别已经回答、仍未知、单一来源和新暴露问题；
- 下一场重点应转向运营可独立回答的信息，例如产值汇总/跨期处理、运营与财务口径边界、重复报数的具体数据和场景；
- 不重复把“HR 组织绩效”作为重点重新问运营；
- 不把 HR 听到的反馈写成企业已验证事实；
- 输出应直接给“更新后的重点/提纲”，而不是先展示完整证据状态表。

### Regression fail examples

- 重新生成一份与前序访谈无关的通用运营提纲；
- 把“存在普遍重复报数问题”当成既定事实追问原因；
- 要求用户先运行或理解 Interview Delta。

---

## Engineering use

每次 Public productization / routing / UX 变更后，至少人工或目标模型复核 C1–C4 是否仍满足上述行为。

正式 Capability Acceptance 仍使用 Skill Manager 预注册的独立 held-out paired evaluation；本文件不能替代该证据。

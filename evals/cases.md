# TalkTrace v0.1 Eval Cases

## Purpose

验证 TalkTrace 是否真正改善咨询顾问的调研访谈结果，而不是仅让输出更长、更像模板。

主要 baseline：

> 同一通用模型 + 同一项目材料 + 同一自然语言任务，但**不加载 TalkTrace**。

正式 Capability Acceptance 由 Skill Manager 完成；本文件只提供可复用测试契约。

---

# Synthetic Case｜云川工程科技有限公司

> 本案例完全虚构，仅用于公开测试，不对应任何真实客户、企业、人员、制度或项目。

## 项目背景

云川工程科技有限公司是一家约 600 人的工程技术服务企业，业务包括规划咨询、工程设计、数字化服务和项目管理。公司近两年业务结构变化较快，管理层希望开展一次“项目经营与绩效协同”专项调研，重点了解：

1. 项目目标如何分解到业务部门和项目负责人；
2. 项目过程数据如何进入部门经营管理；
3. 部门绩效与项目结果如何衔接；
4. 正式制度与实际运行之间是否存在明显差异。

本轮任务仅做调研访谈准备与信息整理，不直接形成正式管理诊断。

## 组织与角色

- **董事长 周岚**：负责战略方向、重大改革和干部管理；
- **总经理 韩启明**：负责经营管理、年度目标与重点项目统筹；
- **人力资源部部长 林悦**：负责绩效管理、薪酬政策和干部考核；
- **经营管理部部长 方知远**：负责经营计划、项目经营数据和回款跟踪；
- **设计一院院长 江屿**：负责大型设计项目交付、部门经营与人员安排；
- **数字业务中心主任 沈宁**：负责数字化产品和新业务项目；
- **财务部副部长 罗嘉**：负责收入确认、成本核算和经营分析；
- **项目经理 许哲**：负责一个重点综合设计项目的进度、协调和项目数据填报。

## 已知材料事实

1. 公司制度规定：年度经营目标由经营管理部组织分解，各业务部门再分解到重点项目。
2. 人力资源部制度规定：部门年度绩效包含经营结果、重点任务和管理指标。
3. 当前资料没有明确说明项目过程数据如何稳定进入部门绩效评价。
4. 经营管理部月报包含合同、产值、回款和重点项目进度。
5. 资料没有说明业务部门负责人是否可以调整项目负责人提交的内部绩效分配建议。
6. 公司希望两天内完成核心访谈；每天可用时间为 09:00—12:00、14:00—17:30；项目组只有一组。

# Case A｜Interview Plan

## Prompt

> 根据以上项目资料，帮我制定访谈计划。

## Expected TalkTrace behavior

### Must
- 先识别访谈对象的信息价值，而不是直接按职位排序；
- 至少覆盖决策层、机制 owner、业务执行者和项目一线视角；
- 对建议访谈对象给出简短访谈目的；
- 使用当前已给出的“两天 / 单组 / 每日时段”约束，不重复询问这些信息；
- 如使用默认访谈时长，应明确其是建议值，可由顾问调整；
- 形成可复制到 Excel/Sheets 的结构化表格；
- 日程不能超出可用时段。

### Must not
- 编造人员可用时间；
- 宣称正式职位等于真实影响力；
- 为了全面而机械把所有人设成同一优先级；
- 在已有时间约束清楚的情况下再次让用户填写整套排程参数。

## Paired comparison focus

相较 no-Skill baseline，重点判断：
- stakeholder 选择是否更可解释；
- 是否减少无效追问；
- 排程是否更符合真实约束；
- 是否明确顾问需要确认的少量关键事项。

# Case B1｜Senior Decision-maker Guide

## Prompt

> 给董事长周岚准备一份 45 分钟的客户发送版访谈提纲。

## Expected TalkTrace behavior

应重点围绕：
- 本轮专项调研的背景、目标和管理层真正希望解决的问题；
- 项目经营与绩效协同希望达到什么管理效果；
- 管理层认为当前最需要验证的关键矛盾；
- 对业务部门和项目负责人的权责边界希望如何把握；
- 本轮调研的改革边界、优先级或不可突破原则。

不应把大量时间用于询问月报字段、具体核算步骤等明显更适合职能 owner 的细节。

---

# Case B2｜Functional Owner Guide

## Prompt

> 给人力资源部部长林悦准备一份 45 分钟的顾问内部版访谈提纲。

## Expected TalkTrace behavior

应明显区别于董事长版本，重点进入：
- 部门绩效如何设计、计算和审核；
- 经营结果、重点任务、管理指标如何形成最终评价；
- 项目过程数据目前在哪些环节进入或没有进入绩效；
- 最近一次实际绩效评价如何操作；
- 业务部门/项目负责人在评价和分配中的实际角色；
- 正式规则与实际执行是否存在例外。

内部版可展示：提问目的、已有事实、可能追问和待验证点。

### Leading-question hard gate

已知“资料没有说明业务部门负责人是否可以调整项目负责人提交的内部绩效分配建议”，因此不得直接问：

> “为什么业务部门负责人会调整项目负责人的分配建议？”

应先中性询问实际流程与角色。

# Case B3｜Business Manager Guide

## Prompt

> 给设计一院院长江屿准备一份 40 分钟的访谈提纲。

## Expected TalkTrace behavior

应围绕业务实际运行，例如：
- 部门经营目标如何落到具体项目；
- 项目进度、产值、回款等信息如何影响部门管理；
- 项目经理与部门负责人如何分工；
- 部门绩效与项目实际结果是否匹配；
- 最近项目中的实际案例、例外和协同堵点。

### Role differentiation hard gate

B1 / B2 / B3 三份提纲如果只是职位名称不同、核心问题大面积相同，则 FAIL。

# Case C｜Interview Notes

## Input transcript

> 受访者：设计一院院长江屿。  
> “现在经营月报数据我们每个月都看，合同和回款比较清楚，项目进度也有。但是绩效考核真正到年底的时候，项目过程数据怎么进去，没有一个大家都能说清楚的固定算法。去年我们院有一个项目，项目经理自己认为进度完成得很好，但回款没有跟上，最后部门评价的时候还是把回款因素看得比较重。这个项目经理就觉得过程贡献没有体现。这个事情我觉得不一定是制度错了，也可能是项目类型不一样，不能都用一把尺子。具体去年评分怎么算的，我现在记不清，要问人力。”

## Prompt

> 把这段访谈整理成专业纪要。

## Must preserve

- 月报包含合同、回款、项目进度；
- 受访者认为年底绩效中项目过程数据进入方式不清晰；
- 一个项目存在“进度较好但回款不足、最终评价较看重回款”的案例；
- “项目经理认为过程贡献没有体现”是案例中的当事人感受，不是客观结论；
- 受访者提出竞争性解释：可能不是制度本身错误，也可能与项目类型差异有关；
- 去年具体评分算法受访者记不清，需要向人力核实。

## Must not

- 写成“公司绩效制度不合理”；
- 写成“项目过程贡献没有进入绩效”这一已验证事实；
- 自行补造评分比例或制度条款；
- 删除“不一定是制度错了”的限定。

# Case D｜Insufficient Information / Degraded Mode

## Prompt

> 我明天要访谈一个客户的人力资源部长，帮我出一份高度针对性的提纲。

## Expected behavior

TalkTrace 不应假装知道项目情况。

可先说明：当前缺少项目目标和客户资料，无法做到真正“高度针对性”。然后只询问最少必要信息，例如：
- 这次项目/访谈主要想解决什么；
- 是否已有组织、职责、制度或项目背景资料可以提供。

如果用户暂时无法提供，可以给一个明确标注为通用初稿的提纲，但不得包装成项目定制结果。

# Case E｜Boundary / Diagnosis Overreach

## Input

使用 Case C 的单次访谈。

## Prompt

> 根据这次访谈直接告诉我，这家公司绩效管理的根本问题是什么？

## Expected behavior

TalkTrace 应拒绝证据越级，但不需要生硬拒答。

应说明：单次访谈可以支持若干**问题线索/待验证假设**，例如：
- 项目过程信息与年度绩效的衔接方式可能不清晰；
- 不同项目类型是否需要差异化评价值得验证；
- 回款与过程贡献的权重/适用条件需要核实。

同时明确：需要结合制度、实际评分数据、其他角色访谈等才能形成正式公司级诊断。

# Release-oriented hard gates

以下任一出现，当前 candidate 不应通过 Capability Acceptance：

1. 重要项目事实被编造；
2. 单次受访者陈述被直接写成企业已验证事实；
3. 三类角色提纲缺乏实质差异；
4. 诱导性问题把未验证假设写成前提；
5. 资料不足时仍输出虚假的高度针对性结果；
6. 用户为了使用 Skill 被迫理解内部工程/状态机制；
7. TalkTrace 相比正常 no-Skill baseline 没有稳定的专业增益；
8. 为实现 v0.1 引入与价值不相称的外部依赖或系统复杂度。

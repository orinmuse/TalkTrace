# Adaptive Probing & Evidence-Fit Regression

## Purpose

验证 TalkTrace 是否能根据实际回答选择下一步追问，并判断证据能支持什么范围。该文件是公开 synthetic regression，不是 sealed Capability Acceptance evidence，也不能证明真实项目价值。

## Synthetic case｜澄川工程咨询公司

以下公司、项目、角色和记录均为虚构。

项目组正在了解项目月度经营数据如何进入部门管理。当前材料只说明：

- 项目经理每月提交项目进度和预计完成情况；
- 运营中心汇总形成月度项目表；
- 现有材料没有说明运营中心是否审核、修改、反馈或追踪项目数据；
- 没有材料说明上述做法是否为稳定机制。

拟访谈运营中心一名业务经理，目标是了解月度数据从提交到进入管理使用的实际过程。

## Stage 1｜Initial guide

**Prompt**

> 给运营中心业务经理准备一份30分钟的顾问内部访谈提纲，重点了解项目月度数据的实际处理过程。

**Expected behavior**

- 先用开放问题还原实际过程，不预设存在审核、修改、反馈或追踪；
- 内部版标明本题要确认的主张和适用范围；
- 可选追问是条件式的，不把所有维度塞进一个长问题；
- 预留现场追问时间。

## Stage 2｜Generic answer

**Interviewer asks**

> 项目经理提交月度进度后，运营中心实际会怎么处理？

**Respondent answer**

> 我们一般都会看一下，发现不太合理的就会调整，最后形成月报。

**Required adaptive next move｜现场访谈阶段**

TalkTrace 应识别这仍是概括性陈述，且“调整”行为、主体、依据和权限尚未明确。此时以源、点、环为主：识别概括性说法及其来源，选择一个最有价值的下一问。不要在现场输出完整的 Source / Point / Line / Surface / Loop 分析，不要生成覆盖矩阵，也不要把内部标签展示给受访者或用户。

优先追问一个最近的具体案例，例如：

> 能否举最近一次实际发生的例子，讲讲当时具体发生了什么？

不得直接问“你们通常由谁审核、按什么权限调整”，因为审核职责和正式权限尚未确认。

## Stage 3｜Branch by answer

### Branch A｜First-hand case

**Respondent**

> 上个月有一个项目把预计完成比例从80%改成了65%，是我们这边的同事提出的，项目经理后来补充了说明。

**Required behavior｜现场访谈阶段**

- 将该事件记录为一个具体案例，不自动升级为稳定机制；
- 现场仍以源、点、环为主，只提出一个最有价值的下一问；不要求当场构建完整关系图或议题覆盖画像；
- 只选择当前最缺且影响判断的一个维度继续追问；如仍需其他信息，分步追问，不把调整依据、参与者、记录和最终结果合并成一串复合问题；
- 如需判断普遍性，再单独询问其他月份/项目是否也有类似情况；
- 不预设提出调整的人拥有正式审核权。

### Branch B｜Second-hand account

**Respondent**

> 具体我没经手，是听同事说有时会调整。

**Required behavior**

- 将其标记为转述，不作为独立佐证；
- 询问最可能的直接经办人或可回查的记录；
- 不继续追问受访者猜测调整流程。

### Branch C｜No knowledge

**Respondent**

> 我不负责这部分，不清楚。

**Required behavior**

- 不将“不清楚”解释为没有相关处理；
- 停止对该受访者追问机制细节；
- 建议转向实际经办人、流程 owner 或相关业务记录。

### Branch D｜Formal document supplied

**Respondent**

> 制度规定运营中心要审核项目月报。

**Required behavior**

- 制度可以支持正式职责/规则存在；
- 继续区分制度规定与实际执行，必要时用一个真实案例验证；
- 不因制度条文直接认定每次都按制度执行。

## Stage 4｜Evidence-fit, scope and independence

**Required checks**

1. 对 Branch A，证据基础为亲历案例，适用范围为单一项目/月份；验证状态只能支持该案例，频率主张仍待验证。
2. 制度文件支持正式规定，不单独证明实际执行。
3. 转述不等于亲历，也不自动构成独立佐证。
4. 多人说法若来自同一会议/上级/文件，不得重复计数为独立来源。
5. 频率主张需要适当的跨案例、连续记录或其他覆盖证据。
6. 权限主张需要适当的正式授权依据和/或实际决策记录。
7. 没有证据或受访者不掌握信息，不等于事项不存在。
8. 对 Branch D，证据基础为正式制度文件，适用范围是制度规定对象；制度设计可以得到支持，但实际执行仍待验证。
9. 分开记录证据基础（文件/数据/亲历/转述/观点）、适用范围（案例/团队/组织/时间）和验证状态（待验证/得到支持/独立佐证/冲突/未解决/满足当前用途），不得合并为一个证据等级。
10. 来源独立性之外，还应考虑来源是否直接接触事件、职责观察范围和是否共享上游信息；不得据此推断受访者动机。

## Stage 5｜Post-interview synthesis｜访谈后跨来源综合

本阶段发生在多场访谈/相关资料已进入当前上下文之后，不属于现场实时追问。以下来源、人员、记录和事件仍全部为虚构。将其作为同一议题的追加资料输入，不另开一个新测试项目。

此时才按需展开完整的源—点—线—面—环：内部区分来源、信息点和关系，形成有限议题画像，并据此选择下一来源。默认用户输出保持简洁；只有用户要求证据综合或来源分析时，才展示必要的关系和覆盖信息。

### Additional sources

| Source | 内容 | 来源属性与边界 |
|---|---|---|
| S1｜月报管理制度 | 制度写明运营中心负责审核项目月报 | 正式制度，只支持制度设计与规定职责 |
| S2｜运营中心业务经理访谈 | “我们一般都会看一下”；并亲历上月某项目预计完成比例从80%调整为65%的讨论 | 概括性说法 + 一个亲历案例；受访者不是最终确认人 |
| S3｜项目经理访谈 | 其本人提交80%后，运营中心要求补充说明；其后看到月报采用65% | 亲历该项目沟通，但不知道最终确认权限 |
| S4｜系统修改记录 | 显示该项目预计完成比例由80%改为65%，由运营中心某账号在指定时间修改 | 系统记录支持字段变更和账号操作，不单独证明授权或审核责任 |
| S5｜部门负责人访谈 | 称“运营中心一直会调整月报”；其依据是此前听运营中心业务经理在例会上介绍 | 转述，与S2共享上游信息，不是独立佐证 |

### Required synthesis

**Source｜源**

- 记录 S1–S5 的来源类型、亲历/转述属性和可用定位；
- 识别 S5 与 S2 的共享上游依赖；
- 不把历史案例或行业惯例作为当前项目事实。

**Point｜点**

至少区分：
- P1：正式制度规定运营中心审核月报；
- P2：运营中心业务经理称“通常会看并调整”；
- P3：某项目某月的预计完成比例由80%变为65%；
- P4：项目经理曾被要求补充说明；
- P5：系统记录显示某运营中心账号修改了字段。

每个点均保留来源及其实际支持范围；不要把 P2 的“通常”当成已证实频率。

**Line｜线**

- S1/P1 只证明制度规定，不证明实际执行；
- S2、S3、S4 对同一具体事件提供不同视角/记录支持，但仍只覆盖该案例；
- S5 复述 S2 的上游信息，不得计为独立佐证；
- S4 能说明账号执行了字段修改，不能单独证明谁拥有正式审核或最终确认权；
- 80%先于65%只能说明顺序，不能自动推断调整原因或效果。

**Surface｜面**

形成有限议题画像：
- 正式制度职责：Covered；
- 单一项目的字段变更事件：在案例范围内得到多来源支持；
- 实际流程的完整步骤：Partially covered；
- 跨项目发生频率：Not covered；
- 最终确认权/授权链：Not covered；
- 全组织普遍机制：Not covered。

不得把“制度存在 + 一个案例 + 多人重复说法”合并成“运营中心通常审核并调整所有项目月报”。

**Loop｜环**

如果本次调研目标包含厘清最终确认权，下一问应只问一个最有价值的问题，例如：

> “这次把预计完成比例调整为65%后，最终由谁确认并作为月报口径？”

如果本次目标只需了解该次事件，则不必为了补齐所有空白继续追问。应根据决策目标选择下一步，而不是机械填满画像。

### Required behavior

- 将原始来源、信息点、关系和有限议题画像分开处理；
- 每个重要点能回到可用来源；没有定位时不造定位；
- 关系类型明确，不把顺序、共同上游或意见一致误当成因果/独立佐证；
- 明确标注议题画像的覆盖边界；
- 新来源进入后更新相关点、线和面，而非只在末尾追加摘要；
- 下一步由最重要的未解决问题决定，且每轮只提出一个最有价值的问题；
- 不向用户输出一张庞大证据图谱或要求维护编号台账。

## Pass criteria

- 下一问随回答变化，而不是每次重复同一固定追问清单；
- 每轮优先问一个最有价值的问题，不把全部追问堆成复合问句；
- 概括性说法优先落到具体案例；
- 亲历、转述、观点、制度和数据不混淆；
- 证据与主张类型、范围和时间匹配；
- 证据基础、适用范围和验证状态分别表达，不混为一个标签；
- Source、Point、Line、Surface 各自边界清楚，Loop 能更新前述层次；
- 现场访谈阶段以源、点、环为主，保持自然的一问一答，不输出完整五层结构或覆盖矩阵；
- 访谈后/跨来源阶段才按需展开线与面，默认仍保持用户输出简洁；
- 信息关系有明确类型，因果假设不冒充事实；
- 议题画像标注覆盖范围，不从单一案例或样本外推；
- 共享上游来源不重复计数；
- 单一案例不被泛化；
- 来源独立性得到检查；
- 不能回答时正确转交下一来源，而不是继续逼问；
- 内部机制不泄漏为用户必须学习的新操作术语；
- 不建立持久状态、数据库、证据图谱或数值评分。
